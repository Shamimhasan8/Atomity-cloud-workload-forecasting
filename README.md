# Cloud Workload Forecasting — Atomity AI/ML Take-Home

End-to-end workload analysis and short-horizon forecasting on the **Microsoft Azure Public Dataset V2** (`data-v1` challenge release): 10,000 VMs × 134 five-minute CPU observations (1,340,000 rows, ≈ 11.1 h per VM).

- **Targets forecast** (final 24 timestamps = 2-hour holdout): `active_vm_count` and `aggregate_cpu_utilization`
- **Final holdout MAE:** 0.000 for the VM count (constant series, see [findings](#important-findings)) and 0.176 pp for aggregate CPU utilization (persistence baseline: 0.147 pp — an honest negative result, dissected in the [report](reports/final_report.pdf))

## 3. Generate predictions (one command)

```bash
python -m cwfc.predict --data challenge_data --output predictions.csv
```

This single command: loads and validates the data → builds the aggregate targets → applies the 110/24 chronological split → refits the **frozen** model configuration on the 110 training timestamps → forecasts the 24 holdout timestamps → validates the output against the SUBMISSION.md contract → writes `predictions.csv`. It reads holdout *timestamps* from the data but never touches holdout *values*, so it cannot leak them.

Useful variants:

```bash
python -m cwfc.predict --data challenge_data --output predictions.csv --select   # re-run CV selection instead of the frozen config
python -m cwfc.predict --data <any_dir> --output out.csv                        # works on any conforming directory, incl. tiny smoke datasets
```

The pipeline has **no hard-coded VM IDs, timestamps or prediction values**: the holdout is always the final 24 timestamps of whatever dataset is supplied (datasets with fewer than 134 timestamps get a proportionally scaled holdout; larger datasets train on everything before the final 24), non-constant VM counts are forecast with the same validated procedure, and dirty rows (duplicates, invalid CPU values) are handled with explicit warnings. The integration tests in `tests/test_predict.py` exercise exactly this with churn-ing, dirty, 60-timestamp, 140-timestamp and holdout-perturbed synthetic datasets — the perturbation test proves that scrambling the holdout readings leaves `predictions.csv` byte-identical.

## 5. Model methodology (decisions and why)

- **Targets** are constructed exactly per `DATASET.md`: `active_vm_count(t)` = distinct VMs with a *valid* reading; `aggregate_cpu_utilization(t)` = mean of valid `avg_cpu` in [0, 100]. Invalid readings (non-finite, out of range) are excluded from both; duplicates are dropped; everything is logged.
- **Validation design:** expanding-window rolling-origin inside the 110 training timestamps — 7 folds, origins every 30 min (indices 50–86), each forecasting a full unseen 24-step horizon, mimicking the production task. A 4-fold variant is reported as a sensitivity check (same winner).
- **Candidate pool (17):** persistence, historical mean, moving averages (6/12/24), drift, seasonal-naive(24), SES (α = 0.3/0.6/0.9), damped Holt, recursive ridge autoregressions (α = 0.1/1/10/100) on past-only lag/rolling features, ridge with lagged per-category segment features, and a regularized gradient-boosted autoregression. Hyperparameter settings are separate candidates on identical folds (no per-fold tuning).
- **Pre-declared selection rule:** lowest pooled CV MAE; ties → simplest model.
- **Frozen configuration** (`cwfc.models.FROZEN_CONFIG`, set before any holdout evaluation):
  - `active_vm_count` → **persistence** (the series is constant at 10,000 — every candidate ties at CV MAE 0; the tie-break picks the simplest, and the pipeline still computes the count from data each run)
  - `aggregate_cpu_utilization` → **ridge autoregression (α = 100), recursive** — a shrinkage-smoother between recent level and historical mean; CV MAE 0.183 pp = **−15.1% vs persistence** (0.215 pp)
- **Documented negative decisions:** no calendar/seasonal features (11 h cannot identify a season; seasonal-naive empirically confirms, CV MAE 0.318); no direct per-horizon regression (data-starved: the h = 24 model would train on ~2 rows); gradient boosting loses (0.224); the segment-augmented recursive ridge *diverges* (CV MAE ≈ 5.4×10³ / 2.7×10⁶ after the stale-feature correction below); weakly regularized recursive ridge explodes (MAE 1.79) — the recursive error-compounding failure mode.
- **Leakage prevention** (tested in `tests/test_features.py` / `tests/test_models.py`): features for time *t* provably use only values before *t*; recursive forecasts feed back predictions only (corrupting the future leaves forecasts bit-identical); folds never touch the holdout; metadata lifetime statistics and deletion timestamps are excluded by design (`cwfc.data.FUTURE_METADATA_FIELDS`).

## 6. Experimental results (measured)

| Target | Model | CV MAE (pp) | Holdout MAE (pp) | Holdout RMSE (pp) |
|---|---|---:|---:|---:|
| active_vm_count | persistence (frozen) | 0.000 | **0.000** | 0.000 |
| aggregate_cpu_utilization | ridge_lag_α100 (frozen) | **0.183** | 0.176 | 0.216 |
| aggregate_cpu_utilization | persistence | 0.215 | **0.147** | 0.185 |
| aggregate_cpu_utilization | historical mean | 0.209 | 0.175 | 0.211 |

**The honest headline:** the frozen model won cross-validation by 15.1% but **persistence beat it on the holdout** (0.147 vs 0.176 pp) after a regime shift (holdout mean 9.27% vs training 9.41%) that CV could not anticipate. We report this as measured, did not retro-fit the frozen configuration, and dissect the failure in notebook 03 and the report: both models under-forecast the shifted regime (bias −0.12 pp: holdout mean 9.27% vs forecast mean 9.15%), residuals are autocorrelated (lag-1 ≈ 0.69), peak error runs 2–3× non-peak error, error triples from the first to the last half-hour of the horizon, and the empirical 80% interval under-covered (67% vs nominal 80%).

**Operational policy**, calibrated on training-window CV residuals only and then evaluated *independently* on the holdout: provision = forecast + 0.5 pp margin (calibration: 97.6% no-shortfall probability, expected shortfall 0.0009 pp; holdout evaluation: **0 of 24 steps short**, the worst under-forecast +0.498 pp covered with 0.002 pp to spare), scale on sustained breaches (forecast + 0.35 pp for ≥ 3 steps; 92.9% no-shortfall on CV, 2/24 breach steps on holdout), band-based headroom at predicted peaks, and 30-minute forecast refresh. Signed demand shortfall (actual − forecast − margin) drives the trade-off, not absolute error. Full derivation in notebook 03 §8 and report §10.

## 7. Important findings

1. **The fleet aggregate is stable by construction of scale**: between-VM spread (≈ 13 pp) dwarfs within-VM noise (≈ 1.4 pp), so 10,000-VM averaging yields a 2% coefficient of variation — that is what makes 2-hour-ahead forecasting feasible at all.
2. **`active_vm_count` is constant at 10,000** — a curation artefact (only complete traces were selected; no VM churns inside the window). The optimal forecast is therefore the constant, and we say so rather than dressing it up as model skill.
3. **11 hours admit no seasonality** — every seasonal assumption is untestable here; the data proves the point (seasonal-naive is among the worst candidates).
4. **Simple, shrinkage-heavy models dominate at this sample size** — and one clean 24-step holdout can still flip the ranking (regime sensitivity). Both facts are reported; the capacity policy absorbs the second with margins and triggers.
5. **Peaks are the least predictable, most costly regime** — the single holdout peak was missed by ≈ 0.5 pp by every model; the policy reserves its widest headroom exactly there.

## 10. Corrections after independent review (and how they were verified)

An independent technical review of the initial submission found three implementation defects plus two presentation errors. All were corrected transparently; **the frozen model, its features and `predictions.csv` are bit-identical before and after** (the winning configuration uses neither segment features nor the affected code paths), and every corrected comparison was recomputed with training-window validation only.

1. **Stale segment features** (`cwfc/features.py`): `features_at_origin` could return an *older* feature row when future segment observations were unavailable (the warm-up `dropna` silently removed the origin row), so segment-augmented recursive models repeated one prediction for all 24 horizon steps — their earlier CV MAE of 0.31–0.33 was an artefact. **Fix:** future segment means are held at their last observed values (leakage-safe last-known-value fill), and the function now fails loudly if the returned feature timestamp does not equal the next timestamp. **Corrected result:** those candidates' true behaviour is recursive divergence (CV MAE ≈ 5.4×10³ and 2.7×10⁶). Regression tests: `tests/test_features.py::TestSegmentFeatureOrigin` (advancing timestamps under recursion, last-known-value semantics, loud failure, non-degenerate forecasts).
2. **Inverted prediction-interval sign** (`cwfc/evaluate.py`): residuals are `r = prediction − actual`, so the interval for the actual value must be `[forecast − Q_hi(r), forecast − Q_lo(r)]`; the old code added the quantiles instead, placing the band on the wrong side of the forecast whenever residuals were biased. **Fix + effect:** all bands, coverage statistics and figures regenerated (holdout coverage 62% → 67%). Regression tests: `tests/test_models.py::TestEmpiricalIntervalSignConvention` (asymmetric residuals, over- and under-forecast cases).
3. **Holdout-contaminated policy calibration** (notebook 03 §8): the capacity margin was originally sized from pooled CV + holdout *absolute* errors. **Fix:** the margin is now calibrated on training-window CV residuals only, using **signed demand shortfall** (`max(actual − forecast − s, 0)`), and the frozen policy is evaluated separately on the holdout (0/24 shortfall steps at s = 0.5 pp; worst under-forecast +0.498 pp covered with 0.002 pp to spare).
4. **Notebook execution errors**: two `ValueError: Unknown format code 'f'` errors (Styler formatting applied to mixed-type columns) were silently recorded in `03_evaluation.ipynb`. **Fix:** numeric formatting is applied only to numeric columns, and a new notebook-execution test (`tests/test_notebooks.py`) re-executes all three notebooks from clean kernels and fails on *any* cell error.
5. **Report wording**: the holdout analysis incorrectly described the −0.12 pp signed bias as over-prediction; both models **under-forecast** the shifted regime (forecast mean 9.15% vs holdout mean 9.27%). All numerical claims were re-audited against executed results. A latent CLI crash for datasets with *more* than 134 timestamps (holdout length ≠ horizon) was also found and fixed (`adaptive_split` now always takes the final 24 timestamps as holdout; covered by tests).

## 11. Limitations

- One 24-step holdout is a single draw from an autocorrelated error process — model rankings at this scale are fragile (measured, not assumed).
- Empirical prediction intervals from 7 overlapping folds are coarse and under-covered under regime shift (67% vs nominal 80% on the holdout).
- No seasonal structure can be identified in 11 hours; margins are valid for short-horizon planning only.
- The curated release contains no churn, so the active-count target is trivial here; production count forecasting needs churn-aware (survival) models.
- See report §11 for future work (online regime-aware selection, calibrated probabilistic forecasts, longer traces).
