## 1. Executive Summary

This report documents an end-to-end forecasting system for two aggregate cloud-workload targets — the number of active virtual machines and the fleet's mean CPU utilization — built on a curated release of the Microsoft Azure Public Dataset V2 and evaluated on a sealed two-hour holdout. Three findings drive the conclusions. First, the fleet's aggregate CPU utilization is a remarkably stable signal (mean 9.41%, σ = 0.19 pp over 110 training timestamps), because ten thousand heterogeneous VMs average their noise away; this makes short-horizon forecasting tractable but sets a hard noise floor. Second, disciplined validation crowned a deliberately simple winner: a heavily regularized autoregressive ridge, selected by pre-declared rules over 17 candidates, cut rolling-origin cross-validation MAE by 15.1% versus persistence — while gradient boosting, seasonal-naive, and segment-feature variants all lost, confirming that with ~100 training points simplicity is a feature, not a concession. Third, the untouched holdout humbled the selection: persistence edged the frozen model (MAE 0.147 vs 0.176 pp) after a regime shift that cross-validation could not anticipate, and demand peaks were missed by roughly 0.5 pp. These negative results are reported as measured and drive the operational policy: a 0.5 pp safety margin calibrated on training-window cross-validation residuals alone (97.6% no-shortfall probability) and then evaluated independently on the holdout (zero shortfall steps; the worst under-forecast covered with 0.002 pp to spare), sustained-breach scaling triggers, full band headroom at predicted peaks, and 30-minute forecast refresh. The submission ships as a reproducible repository: one command regenerates `predictions.csv`, 67 automated tests (including property-based leakage tests, holdout-perturbation invariance, and end-to-end notebook execution) protect the protocol, and all code, notebooks and figures are committed. An independent review of the initial submission found three implementation defects (stale segment features, an inverted prediction-interval sign, and a holdout-contaminated policy calibration); all three were corrected and are documented transparently in §11, without touching the frozen model or its predictions.

## 2. Problem Definition

Cloud capacity teams must decide, continuously, how much compute to hold for the near future: too little and latency-sensitive work degrades; too much and capital idles. The challenge formalizes this as a short-horizon, multi-step forecasting problem on five-minute aggregate telemetry: given the first 110 timestamps of a 134-timestamp (≈11.1 h) workload trace, forecast the final 24 timestamps (two hours) of (i) `active_vm_count`, the number of distinct VMs with a valid CPU reading at each timestamp, and (ii) `aggregate_cpu_utilization`, the mean of VM-level average CPU readings, a percentage in [0, 100]. The protocol forbids using the final 24 observed values for fitting, tuning, or selection, and requires time-aware validation; submissions must be reproducible from a clean checkout and robust to a reviewer-supplied smoke dataset. We treat this as the operational question it mirrors — *how predictable is aggregate demand, what does the forecast error cost, and what should an infrastructure team do with it* — rather than as a leaderboard exercise.

## 3. Dataset Understanding

The `data-v1` release contains `vm_cpu_readings.csv.gz` (1,340,000 rows: `timestamp` in seconds, `vm_id`, `min_cpu`, `max_cpu`, `avg_cpu`) and `vm_metadata.csv.gz` (10,000 rows: subscription/deployment identifiers, creation and deletion timestamps, lifetime CPU statistics, `vm_category`, vCPU and memory buckets). Independent verification confirmed every stated guarantee: exactly 134 observations per VM on a perfect 300-second grid spanning 0–39,900 s; zero duplicate `(vm_id, timestamp)` pairs; zero missing values; all `avg_cpu` within [0, 100] with `min ≤ avg ≤ max` throughout; and identical VM populations across the two files. SHA-256 checksums verified against the published `SHA256SUMS`. Two structural properties shape everything downstream. The curation retained only complete traces, so **no VM churns within the window** — the earliest deletion occurs 600 s after it ends — making `active_vm_count` a constant 10,000 by construction. And the metadata's lifetime statistics (`avg_cpu`, `max_cpu`, `p95_max_cpu`) and deletion timestamps summarize the *entire* VM lifetime; relative to any forecast origin inside the window they are **future information** and are excluded from all features by design, and enforced by a dedicated module constant and unit test.

## 4. Preprocessing Methodology

The pipeline (`src/cwfc/data.py`) loads both files, validates schemas and cross-file population identity, and raises a typed `DataValidationError` on contract violations (missing/unexpected columns, mismatched VM sets, duplicate metadata rows) so failures are loud, never silent. Row-level cleaning handles the cases the curated release happens not to contain but production data would: duplicate `(vm_id, timestamp)` records are dropped keeping the first occurrence; readings with non-finite or out-of-range `avg_cpu` are flagged invalid and excluded from both targets; and rows are sorted chronologically. Targets are then constructed exactly per the dataset contract: `active_vm_count(t)` counts distinct VM IDs with a valid reading (each VM at most once), and `aggregate_cpu_utilization(t)` is the mean of valid `avg_cpu` values, with timestamps taken from the data rather than an assumed grid. Every decision is logged in a human-readable preprocessing report that the prediction CLI prints on every run. The full 134-timestamp series is split positionally 110/24 into training and sealed holdout windows; internal gaps, if any, would be interpolated linearly on the time axis with an explicit warning. Eleven unit tests cover these behaviours, including deliberately dirty synthetic inputs.

## 5. Exploratory Findings

Exploratory analysis (notebook `01_eda.ipynb`) established five facts. **All EDA is computed on the 110-point training window exclusively** — the holdout values are never loaded, plotted or summarized during model development and are unsealed only in the evaluation notebook. **(i) Heterogeneity stabilizes the aggregate.** VM-level `avg_cpu` is heavily right-skewed (median 5.1%, p99 87%); between-VM spread (std of VM means ≈ 13 pp) is ten times the median within-VM fluctuation (≈ 1.3 pp), so averaging 10,000 VMs yields a smooth fleet signal with a coefficient of variation of only 2%. **(ii) No seasonality is identifiable.** The 11.1 h window is under half a day; calendar features would extrapolate structure the data cannot show, so none are used. **(iii) The aggregate is persistent and mildly mean-reverting** (lag-1 autocorrelation 0.67, decaying to ≈ 0.39 by lag 8; differenced-series lag-1 autocorrelation −0.16), motivating smoothing and regularized-autoregressive model families. **(iv) Peaks cluster but do not cycle**: demand highs form a sustained 30–45-minute plateau mid-window while the training window *ends* near its minimum — a concrete risk for last-value anchoring. **(v) Segments differ in level and volatility**: Interactive VMs (31% of the fleet) run hotter (11.4% vs 8.2% for Delay-insensitive), and the small Unknown segment is three times more volatile relative to its level; the metadata shape distribution (75% of VMs are 2-vCPU) implies fine-grained scaling steps.

## 6. Forecasting Methodology

Seventeen candidates were compared under identical folds: persistence; historical mean; moving averages (windows 6/12/24); drift; seasonal-naive (period 24); simple exponential smoothing (α ∈ {0.3, 0.6, 0.9}); damped Holt; recursive ridge autoregressions (α ∈ {0.1, 1, 10, 100}) over lag {1, 2, 3, 6, 12, 24}, trailing rolling mean/std {3, 6, 12}, recent differences and a local slope; the same ridge with lagged per-category segment means; and a heavily regularized gradient-boosted autoregression. Hyperparameter settings enter as separate candidates on the same folds — no fold's own validation data selects its hyperparameters. Two exclusions are documented negative decisions: direct per-horizon regression is data-starved (the h = 24 model would train on as few as two supervised rows at the earliest origins), and no calendar/seasonal features are constructed because the window cannot identify them. For `active_vm_count` the constant series makes every candidate trivially exact; the pre-declared tie-break (lower complexity) selects persistence, and the pipeline still computes the count from data on every run, so churning smoke datasets receive genuinely validated forecasts. Recursive models feed back **predictions only**; property tests verify that corrupting all future values leaves forecasts bit-identical.

## 7. Temporal Validation Strategy

Validation mirrors the production task exactly: an expanding-window (rolling-origin) design inside the 110-point training window, origins every 30 minutes from index 50 to 86, seven folds, each fit only on the fold's past and each forecasting a full unseen 24-step horizon. Consecutive validation windows overlap — unavoidable when 110 points must cover a 24-step horizon — so a coarser 4-fold design (step 12) is reported as a sensitivity check; the winner is unchanged. Peak-period error uses a leakage-safe threshold (fold-training μ + σ), and the selection rule is pre-declared: lowest pooled CV MAE, ties broken by simplicity. Automated leakage tests guard all four constraint classes: features for time *t* provably use only values before *t* (verified by perturbing the future and asserting feature rows are unchanged); holdout timestamps never enter any fitting frame; folds are strictly ordered and never overlap the holdout; and no lifetime metadata statistics appear in any feature frame. The final 24 holdout values are unsealed only in the evaluation notebook, after the model, features and configuration are frozen in code (`cwfc.models.FROZEN_CONFIG`).

## 8. Model Results versus Baselines

| Target | Model | CV MAE (pp) | Holdout MAE (pp) | Holdout RMSE (pp) | vs persistence |
|---|---|---:|---:|---:|---:|
| active_vm_count | persistence (frozen) | 0.000 | 0.000 | 0.000 | perfect (0/0 undefined) |
| aggregate_cpu_utilization | ridge_lag_α100 (frozen) | **0.183** | 0.176 | 0.216 | +19.7% worse |
| aggregate_cpu_utilization | persistence | 0.215 | **0.147** | **0.185** | 1.000 |
| aggregate_cpu_utilization | historical mean | 0.209 | 0.175 | 0.211 | +18.9% worse |

Cross-validation told a coherent story: the α = 100 ridge — effectively a shrinkage-smoother interpolating between recent level and historical mean — won pooled CV MAE by 15.1% over persistence, best or near-best in five of seven folds, and the ranking survived the 4-fold sensitivity design. The negative findings were equally instructive: gradient boosting lost (CV MAE 0.224); seasonal-naive was among the worst (0.318), empirically confirming the no-seasonality reasoning; the segment-augmented recursive ridge *diverged* (CV MAE ≈ 5.4×10³ at α = 10 and ≈ 2.7×10⁶ at α = 1 — see the correction note in §11); and weakly regularized recursive ridge exploded (MAE 1.79, RMSE 6.66) — the textbook recursive error-compounding failure. On the sealed holdout, however, persistence won: the honest headline of this submission. The frozen configuration and `predictions.csv` were **not** retro-fitted after observing this; the gap between validation and holdout is itself the most important measured result, and §9 dissects it.

## 9. Error and Failure Analysis

The holdout's regime differed from training: mean utilization dropped from 9.41% to 9.27%, sitting *below* the training mean but *above* both models' forecast anchors — so **both models under-forecast** (forecast mean 9.148% vs holdout mean 9.269%; signed bias −0.12 pp for the frozen ridge, −0.10 pp for persistence). The frozen ridge anchors on the recent low regime and then drifts further down across the horizon (9.21% → 9.09%), which makes its under-forecast marginally larger than persistence's flat anchor at 9.165%; persistence wins this window not because it is smarter but because the regime happened to sit almost exactly on the last observed value. Both models missed the single ≥ μ+σ peak (9.64% at step 16) by ≈ 0.5 pp — nothing in the preceding trajectory announced it — and peak error ran 2–3× non-peak error in every setting. Residuals are biased low and strongly autocorrelated (lag-1 ≈ 0.69): errors arrive in 30–60-minute runs, not isolated five-minute slips. Error grows with horizon (holdout MAE 0.11 pp in the first half-hour versus 0.31 pp in the last), and the empirical 80% prediction band under-covered (67% vs nominal 80%; seven of the eight misses on the upper side during the late-horizon recovery, one on the lower side from an early 8.98% dip). Operationally: single-window model rankings are fragile (the 0.03 pp gap between models is smaller than the fold-to-fold CV spread of 0.10–0.33), demand spikes are the least predictable and most costly regime, and a production safeguard should monitor *sustained* bias rather than single-step error — which the recommended policy does.

## 10. Operational Recommendations

The policy is derived in two strictly separated steps. **Calibration uses training-window CV residuals only** (the same data that selected the model): with the signed demand error e = actual − forecast (positive = demand above forecast), provisioning forecast + s yields shortfall max(e − s, 0) and idle capacity max(s − e, 0); the margin is chosen from the frozen model's 168 CV residuals. **The frozen policy is then evaluated once on the sealed holdout** — those numbers are measurements, not feedback. The rules: **(1) Provision target** — capacity = forecast + 0.5 pp safety margin, refreshed every 30 minutes (calibration: 97.6% no-shortfall probability, expected shortfall 0.0009 pp, worst CV shortfall at that margin 0.084 pp; ≈ 5.3% relative headroom at the fleet's 9.4% mean). **(2) Scaling trigger** — if realized utilization exceeds forecast + 0.35 pp for three consecutive five-minute steps, scale one step reactively (calibration: 92.9% no-shortfall; the 0.69 residual autocorrelation makes sustained breaches the reliable regime-shift signal). **(3) Peak headroom** — when the forecast reaches the training μ+σ threshold, reserve the point forecast plus the full empirical band rather than the margin. **(4) Segment weighting** — hold Interactive capacity at forecast + margin (latency-sensitive, 31% of VMs) while allowing Delay-insensitive work to run up to 15 minutes behind (schedulable, 62%). **(5) Refresh cadence** — re-fit and re-forecast every 30 minutes and retire the second half of each forecast. **The independent holdout evaluation confirms the calibration**: at s = 0.5 pp, zero of 24 steps fall short — the single worst under-forecast (+0.498 pp at the step-16 peak) is covered with 0.002 pp to spare — while the cheaper s = 0.35 pp leaves a measured 2/24 steps short (max 0.148 pp). Supported by this dataset: the calibration curve and its holdout evaluation, error magnitudes and their horizon/peak dependence at 10,000-VM scale, autocorrelated errors, segment composition. Assumed for production: the idle-versus-unmet cost ratio (the 0.5 pp choice assumes under-provisioning is costlier for latency-sensitive work); churn behaviour (absent here by construction — real active-count forecasting needs survival/reservation lead times); and daily/weekly seasonality (invisible in 11 hours; needs weeks of history).

## 11. Limitations, Corrections and Future Work

Four limitations bound the conclusions. A single 24-step holdout is one draw from a highly autocorrelated error process — persistence's holdout win is evidence about this window, not a significant ranking. The empirical prediction intervals, built from seven overlapping folds, are coarse and under-cover under regime shift; conformal or quantile-regression intervals on richer history would calibrate better. The 11-hour window admits no seasonal structure, so the policy's margins are valid for short-horizon planning only. And the curation's complete-trace selection removes churn, making the active-count target trivially constant; production deployments need churn-aware count models. **Corrections after independent review (documented transparently):** (i) `features_at_origin` could return a *stale* feature row when future segment observations were unavailable, silently making segment-augmented recursive models emit one repeated prediction (CV MAE 0.31–0.33 was therefore an artefact); the corrected implementation forward-fills segment features to their last observed values — a leakage-safe last-known-value treatment — and fails loudly if the feature timestamp does not advance, whereupon the true behaviour of those candidates emerged as recursive divergence. (ii) The empirical prediction interval used an inverted sign convention; with residuals r = prediction − actual the interval for the actual value is [forecast − Q_hi(r), forecast − Q_lo(r)], and all bands, coverage statistics and figures were regenerated (holdout coverage 62% → 67%). (iii) The capacity margin was originally calibrated on pooled CV + holdout errors and measured absolute error; it is now calibrated on CV residuals only with *signed* demand shortfall and evaluated separately on the holdout. None of these corrections touched the frozen model, its features or its predictions — `predictions.csv` is bit-identical before and after — because the winning configuration uses neither segment features nor the affected code paths; every corrected comparison was recomputed with training-window validation only. Future work, in order of expected value: (i) online model selection that tracks regime (discounted errors or a persistence-fallback trigger on sustained bias); (ii) probabilistic forecasts with calibrated intervals; (iii) segment-level and quantile models on longer traces; (iv) integrating the margin policy with real cost functions and autoscaler latency.
